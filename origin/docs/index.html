THE DESIGN

One contribution contract.
Many project architectures.

CVAS does not impose a project's domain model. It carries the contribution mechanics and assurance discipline; each adopting project supplies its own semantics, requirements, reference data and authority.

⌘

Contract before code

Typed inputs and outputs, interfaces, preconditions, postconditions, invariants, state ownership, dependencies and failure behaviour travel with every component.

Read the contract ↗
◎

Verification by default

Manifest checks, executable tests, independent reference cases, mutation testing, bounded execution and explicit PASS / FAIL / INCOMPLETE outcomes.

Replaceable by design

Declared dependencies and stable interfaces make components substitutable. Withdrawal preserves provenance and moves affected workflows to a safe state.

CONTRIBUTOR JOURNEY

From a simple idea to a
reviewable contribution.

The contributor does not need to understand the whole platform or configure a toolchain. The harness provides the rails.

01

Fork

Fork the project. CI starts on pushes and pull requests.

02

Describe

Choose a bounded task and declare the component contract.

03

Build

Implement directly or use AI assistance to scaffold code, tests and documentation.

04

Verify

Run the same harness in the fork or through the browser-only Colab notebook.

05

Submit

Open a pull request. Upstream repeats checks and routes review by risk.

Contributor skill is not the trust mechanism.The artifact must satisfy the contract and the project's assurance policy, regardless of who or what produced it.
ASSURANCE MODEL

Low entry threshold.
High acceptance threshold.

110% is a verification policy: go beyond happy-path checks. It is not a claim of 110% code coverage or a mathematical proof of correctness.

CLASS A

Replaceable

Isolated components with bounded effects and no privileged authority. Automated contract, boundary, negative, mutation and regression checks.

Human review may be raised by project policy.
CLASS B

Significant

Important workflows, broad dependants or consequential data. Adds dependency-impact analysis and independent technical review.

Review is required before upstream acceptance.
CLASS C

Critical

Trust kernel, safety boundary, authority, evidence integrity, canonical state or release control.

Complete human change examination and two independent approvals.

Risk class is not self-awarded by the contributor. The adopting project can raise a classification. A green CI run is evidence of checks performed, not merge permission, certification or deployment authority.
