HUMAN + AI CONTRIBUTION

Contribute a component.
Let the harness do the heavy lifting.

Contributors do not need to understand the whole adopting platform. They need a bounded task, a declared contract and an artifact that can be verified.

Quick path

  1. Fork the adopting repository. The supplied GitHub Actions workflow runs on pushes and pull requests.
  2. Copy the starter files from templates/ and give the component a stable ID and version.
  3. Describe purpose, runtime, interfaces, inputs, outputs, assumptions, invariants, state ownership, dependencies and failure behaviour.
  4. Implement the capability. AI assistance may generate code, tests, examples and documentation.
  5. Add independent reference cases, boundary tests, negative tests and a mutation test.
  6. Run CI in the fork or open the Colab notebook and upload the component ZIP.
  7. Open a pull request. Upstream repeats checks and routes review according to project risk policy.

What to submit

  • manifest.json - machine-readable contract and risk declaration.
  • Implementation entrypoint - executable capability, not a placeholder status response.
  • Test suite - tests that call the implementation and detect incorrect behaviour.
  • Mutation test - evidence that the suite rejects a deliberately incorrect implementation.
  • Reference vectors - expected results derived independently where feasible.
  • Documentation - limitations, assumptions, dependencies and replacement procedure.

Human review

Class B requires independent technical review. Class C requires a complete examination of the change set and two independent approvals, including a domain-authorised reviewer. Configure CODEOWNERS and protected-branch rules in the adopting repository; the generic workflow cannot enforce repository permissions by itself.

Do not add secrets to fork workflows. Untrusted code must run without repository secrets, privileged tokens or access to private files. Colab is not a hostile-code sandbox. Use isolated infrastructure for hostile or high-risk execution.

Repository setup checklist

  • Replace OWNER/REPOSITORY placeholders in links and notebook instructions.
  • Set the real default branch and configure required CI status checks.
  • Replace CODEOWNERS placeholders with actual GitHub handles.
  • Enable two approvals and the appropriate reviewer teams for Class C paths.
  • Configure trusted release signing and deployment separately from fork CI.
  • Add project-specific schema, reference and integration tests.
